M-VAST 3 Application Manual

Version: 2.0_2026_10_23

Authors: Brock Pluimer (University of California, Irvine) & Steven Harte (University of Michigan)

Installation & Setup

In order to run this application, you need Python 3 installed on your system (3.11 or newer recommended on Windows, for finer-grained timing). We also recommend setting your device to maximum brightness before starting the experiment.

Required Packages

Install the required packages by running the following command in your terminal:

pip install pygame pillow numpy ttkbootstrap

Running the Application

Once the packages are installed, run the application with:

python mvast3.py

1. Overview

The Michigan Visual Aversion Stress Test (M-VAST 3) is a software platform designed for conducting quantitative sensory testing (QST) using visual stimuli. It allows researchers to:

  1. Generate standardized and randomized experiment protocols.
  2. Run experiments with participants in a controlled, full-screen environment, either the standard rated paradigm or the continuous tonic fMRI run synced to the MRI scanner trigger.
  3. Collect and Log participant ratings for discomfort and brightness in a structured CSV format.

This manual will guide you through the complete workflow, from setting up an experiment to understanding the data you collect.

2. The Workflow

We recommend setting your brightness to its maximum before starting the experiment. Using the M-VAST 3 application involves two main stages: first generating the experiment files, and then running the experiment with a participant.

Stage 1: Generate Experiment Setup

This is the first step. Here, you define the parameters for your study and create the necessary files.

  1. Launch the M-VAST 3 application. From the main menu, click "Generate Experiment Setup".
  2. Fill in the following fields in the "Generate Experiment Setup" window:
    • Experiment ID: A unique identifier for your study or condition (e.g., Study1_HighAnxietyGroup). This ID determines the randomization and naming of your setup files. Do not use special characters like /\:*?"<>|.
    • Base Output Directory: The main folder where all experiment-related files (setups, schedules, and later, participant data) will be stored. It defaults to an experiment_data folder next to the application. It is recommended to keep this default.
    • Trial Order:
      • Standard fixed order (recommended): every participant gets the same pseudo-random order, and bright trials (brightness 0.8 or higher) are never back-to-back, including across block boundaries. The order is shown as a bar preview.
      • Generate a new order: advanced; choose a seed and whether to space out bright trials. The same seed always gives the same order.
    • Parameter Mode:
      • Default Parameters: Uses a standard, pre-defined set of parameters for trial timing and stimulus frequency. This is recommended for ensuring consistency across studies.
      • Custom Parameters: Allows you to manually set the Stimulus Duration, Fixation Duration, Checkerboard Frequency, and the Number of Randomized Blocks.
  3. Click the "Generate Experiment Files" button.

This action creates two important files inside your "Base Output Directory":

  • ..._brightness_schedule.csv: A CSV file containing the randomized sequence of brightness levels for the main trials, kept for your records. The order is reproducible from its seed.
  • ..._master_trials.csv: The master plan for the entire experiment. This CSV lists every single trial in order, detailing its parameters (brightness, duration, block number, etc.). This is the file you will load in the next stage.

If a master trial CSV with the same Experiment ID already exists, you are asked whether to keep it, save the new one under a new name (e.g. Study1_v2), or overwrite it. Overwriting changes the file's SHA-256, so it would no longer match the hash logged by participants who already ran.

Stage 2: Run Experiment

Once your setup files are generated, you are ready to run the experiment with a participant.

  1. From the main menu, click "Run Experiment".
  2. Fill in the following fields in the "Run Experiment" window:
    • Master Trial CSV: Click "Browse..." and select the ..._master_trials.csv file you created in Stage 1. It is checked straight away: the number of trials, whether every value is in range, the estimated session length, and a short SHA-256.
    • Participant ID: Enter a unique identifier for the participant (e.g., P001, Subj_12). Do not use special characters. If data for this ID already exists in the log folder you are warned (with that file's run status); nothing is ever overwritten.
    • Stimulus Image Files (Image 1 & Image 2): These default to the canonical blue/yellow pair, acheck_by.png and acheck_by_.png. Thumbnails are shown, and each file's SHA-256 is logged.
    • Display: Choose the screen the participant sees. Identify shows each display's number on that screen for 2 seconds. In Extend mode with the laptop as the main display, pick the EIZO here.
    • Participant Data Log Directory: Choose the folder where this specific participant's data will be saved. It defaults to a participant_runs subfolder within your base directory.
  3. Review the Pre-flight Check: display resolution (the protocol expects 1600×1200), refresh rate and frames per flicker half-cycle (7.5 Hz is exactly 4 frames at 60 Hz), free disk space, images, and any existing data for the participant.
  4. Click the "Start Experiment" button. If the chosen display is not 1600×1200 you are asked whether to continue; the answer is recorded in Display_Check.

The control panel will disappear, and the full-screen experiment will begin on the chosen display. When the run ends, a Run Summary shows the run status, trials completed, timing checks (any trial with a stall or catch-up flip is listed), whether the window lost focus, and the files written, with an Open Folder button.

Settings (CSV, images, display, folder) are remembered for the next session unless you untick Remember these settings. They are stored in mvast3_settings.json next to the application.

Windows display scaling: set the participant display's scaling to 100%. At other settings the display reports a smaller size (e.g. 1280×960 at 125%) and the stimulus is scaled.

Tonic fMRI Run

Use "Run Tonic fMRI" instead of "Run Experiment" for the continuous, constant-brightness run acquired during fMRI. No master CSV is needed and no ratings are collected.

  1. Enter the Participant ID and scanner/site, check the images (canonical pair by default), and set brightness, flicker frequency (7.5 Hz is the reference), duration (default 360 s) and the trigger key (default 5). The hint next to the frequency shows how many display frames each half-cycle lasts.
  2. Click Test Trigger… and start a scan (or press the key): it listens for 10 seconds and reports how many pulses arrived and the interval between them (the TR).
  3. Choose the display and click Start Tonic Run. On the intro screen the operator presses SPACE. Trigger pulses are ignored there, so a scanner that is already running can't use up a volume.
  4. The "waiting for scanner" screen appears. The first trigger pulse starts the flicker. The log file is written immediately (Run_Status=running) and rewritten when the run ends.

3. The Participant's Experience

The participant interacts with a simple, full-screen interface.

  1. Instructions: A welcome screen with instructions appears first.
  2. Trial Sequence: The experiment proceeds through a loop for each trial:
    • Fixation Cross (+): The participant is instructed to focus on a cross in the center of the screen.
    • Stimulus Presentation: The flickering checkerboard is displayed for the duration specified in the master trial file.
    • Unpleasantness Rating: A slider appears. The participant uses the mouse to rate the unpleasantness of the stimulus on a scale from 0 (Not Unpleasant) to 100 (Most Unpleasant Image Imaginable) and clicks "Confirm".
    • Brightness Rating: A second slider appears. The participant rates the perceived brightness from 0 (No Image Visible) to 100 (Brightest Image Imaginable) and clicks "Confirm".
  3. Completion: After the final trial, a "Thank You" message is displayed, and the application closes the experiment window.
Exiting the Experiment: The participant or researcher can press the ESC key at any time to stop the experiment. All data collected up to that point will be saved and the file records Run_Status = aborted. Closing the stimulus window (e.g. Alt+F4) is treated the same way and returns you to the menu.

4. Output Data Format

For each participant run, two files are generated in the specified "Participant Data Log Directory".

v2 format change (additive only): every row and column from earlier versions keeps its name and order. New header rows were added after Image2_File, which pushes the trial table down 11 rows. Analysis scripts should find the table by its header line (Trial_Number_Overall,...) rather than by row number. New trial columns were added to the right of the original ten.

A. Detailed Trial-by-Trial Data

Filename: data_P[ParticipantID]_[Timestamp].csv

This file contains a detailed log of every completed trial. It includes a header with metadata about the run, followed by the data columns:

  • Header Information:
    • App_Version: The version of the M-VAST 3 software used.
    • Experiment_ID: The ID of the experiment setup used.
    • Participant_ID: The ID of the participant.
    • Timestamp_Start_Run: The date and time the run was initiated.
    • Master_CSV_Used: The filename of the master trial list.
    • Image1_File / Image2_File: The filenames of the stimulus images.
    • Master_CSV_Path / Master_CSV_SHA256: Full path and SHA-256 hash of the trial file actually used.
    • Trials_Expected: Number of trials in that file.
    • Display_Size, Display_Refresh_Hz_OS, Display_Check: The stimulus window size, the refresh rate the operating system reports, and the resolution check (OK 1600x1200, or MISMATCH … with whether the operator chose to continue).
    • Display_Index, Display_Refresh_Hz_Measured, Vsync: Which display was used (0 = first), the refresh rate measured by timing flips at start-up, and whether flips were synced to the display refresh.
    • Image1_SHA256 / Image2_SHA256: Hashes of the stimulus images.
  • Data Columns:
    • Trial_Number_Overall: The trial number in the overall sequence (1, 2, 3...).
    • Block_Number: The block number. Block 0 is the initial ramp-up block. Blocks 1, 2, etc., are the randomized blocks.
    • Trial_In_Block: The trial number within the current block.
    • Brightness_Factor: The brightness multiplier used for the stimulus (0.0 to 1.0).
    • Stimulus_Duration_s: The duration of the stimulus in seconds.
    • Fixation_Duration_s: The duration of the fixation cross in seconds.
    • Checkerboard_Hz: The flicker frequency of the stimulus.
    • Discomfort_Rating_0_100: The participant's unpleasantness rating (integer from 0-100).
    • Brightness_Rating_0_100: The participant's brightness rating (integer from 0-100).
    • Response_Timestamp: The exact time the final rating for the trial was confirmed.
    • Stim_Onset_s / Stim_Offset_s: Stimulus onset (first frame) and offset (end of the stimulus loop), in seconds since the participant's start keypress.
    • Actual_Stimulus_Duration_s: Offset minus onset.
    • N_Flips: Number of frames that changed the image, including the first.
    • Median_Interval_ms, Min_Interval_ms, Max_Interval_ms: Time between successive flicker transitions (nominal: 66.7 ms at 7.5 Hz).
    • N_Intervals_Over_1p5x / N_Intervals_Under_0p5x: Intervals longer than 1.5× the nominal half-period (visible stalls) or shorter than 0.5× (flips too brief to see).
    • Focus_Lost_Events: Times the stimulus window lost focus or was minimized during the trial (fixation, stimulus and ratings).
  • Footer:
    • Run_Status: completed, aborted (ESC or window closed) or error (for example, a failed write when a USB drive drops, which now stops the run). A file with no Run_Status row means the process died mid-run.
    • Trials_Completed: Number of trial rows written.
    • Timestamp_End_Run: Always the last row.
Timing caveats. Onset/offset and flip intervals are software timestamps taken right after each screen flip, not the moment light leaves the screen. Each rig needs a one-time photodiode check for absolute onset latency. Image changes follow a fixed time grid aligned to display frames, so a system stall appears as one long interval (counted in N_Intervals_Over_1p5x) and never as a burst of catch-up flips. The first image is shown at onset, so Actual_Stimulus_Duration_s should be very close to the requested duration. No image is ever left on screen for less than half a half-period: after a stall the loop skips ahead rather than flashing an image briefly. One limit of software timestamps: if a stall happens just after a screen update but before the time is read, that timestamp is late, so the log shows a long interval followed by a short one even though the screen was fine. Read an over-1.5× interval immediately followed by an under-0.5× interval as a single stall.
Brightness factor. Brightness_Factor multiplies pixel values, not luminance. On a typical display (gamma about 2.2), a factor of 0.1 gives roughly 0.6% of full luminance, 0.6 about 33%, and 0.8 about 61%. Each site should measure its display's luminance at each level with a photometer rather than assume the factor is proportional to light output.

B. Summary Score Data

Filename: summary_P[ParticipantID]_avg_scores_[Timestamp].csv

This file provides a quick summary of the participant's average scores across all completed trials.

  • Participant_ID: The ID of the participant.
  • Number_Of_Rated_Trials: The total count of trials for which ratings were provided.
  • Average_Discomfort: The average of all discomfort ratings.
  • Average_Brightness: The average of all brightness ratings.
  • Run_Status: Same value as in the data file (added at the end).

C. Tonic fMRI Log

Filename: tonic_P[ParticipantID]_[Timestamp].csv

Run parameters, then an event table with wall-clock times and seconds relative to the scanner trigger. It is first written when the trigger arrives (Run_Status = running) and rewritten at the end.

  • Header: as before, plus Display_Size, Display_Refresh_Hz_OS, Display_Check, Display_Index, Display_Refresh_Hz_Measured, Vsync and the image hashes (added after Run_Status).
  • Stimulus_Onset: The measured first frame (in v1 this repeated the trigger time). Actual_Stimulus_Duration_s is measured from this onset.
  • Pre_Stimulus_Gap_s: Time from the trigger to the first frame.
  • Flip statistics, as in the standard run: N_Flips, the interval median/min/max and the over/under counts, plus Focus_Lost_Events.
  • N_Trigger_Pulses_During_Run, then one Scanner_Pulse row per pulse received during the stimulus, so the starting volume can be worked out afterwards.
